# ADR-001：八个驾驶舱模块采用唯一事实所有权

## 背景

产品大纲已经确认八个驾驶舱模块，但“资源配置与工具维护”“安全回溯与黑匣子”“任务控制与进程控制”等概念容易在设计和代码中重复出现。用户不需要承担技术边界判断，因此需要先给后续 AI 和开发工作建立稳定的所有权规则。

## 决定

保留八个模块，并把“安全与回溯系统”更名为“安全与自主策略”。每一类核心事实只能由一个模块拥有，其他模块通过统一状态、事件或引用使用它。

| 模块 | 唯一事实所有权 |
|---|---|
| 总状态仪表 | 聚合状态、告警、预算和唯一下一步 |
| 资源与能力中心 | Provider、凭据、Harness 能力与兼容配置 |
| Agent 机组 | Agent 目录、能力、角色、当前机组和对话入口 |
| 项目与任务系统 | 项目边界、任务目标、执行批次和验收定义 |
| 飞行控制 | 启动、暂停、继续、接管、终止和进程监督 |
| 安全与自主策略 | 安全区、限制、保守自主、常设规则和关键决定 |
| 工具与维护舱 | 发现、安装、健康检查、更新、修复、停用和卸载 |
| 黑匣子与恢复 | 事件、日志、Diff、检查点、报告和恢复操作 |

AI 护航是跨模块能力，不作为第九个模块；统一状态与事件是共享地基，不由任一页面私有。

## 边界判定规则

遇到归属不清时，按它最终回答的问题判定：

- “现在整体怎么样、下一步做什么”归总状态仪表；
- “系统拥有什么能力、如何配置”归资源与能力中心；
- “谁来做、能做什么”归 Agent 机组；
- “要完成什么、怎样算完成”归项目与任务系统；
- “现在启动、暂停、继续还是停止”归飞行控制；
- “是否允许、在什么限制内自动做”归安全与自主策略；
- “软件是否安装、健康、可更新或可卸载”归工具与维护舱；
- “发生过什么、改了什么、怎样恢复”归黑匣子与恢复。

同一个操作可以在多个页面出现入口，但其规则、状态和持久化只能落在唯一所有者中。

## 结果

### 正面结果

- 后续 AI 可以用明确规则拆代码和数据模型，不让相同功能重复实现。
- 页面可以按用户任务组合能力，同时保持底层事实一致。
- 安全政策与审计恢复分离，既能解释“为什么允许”，也能证明“实际发生了什么”。

### 代价

- 需要一套统一状态与事件基础支撑跨模块引用。
- 页面层不能为了开发方便私自保存业务状态。
- 模块之间需要显式接口，早期会增加少量设计工作。

## 未选择的方案

- **合并为更少模块**：短期看起来简单，但会让配置、执行、安全和恢复重新耦合。
- **按页面自由划分**：页面变化会反复改变业务边界，不利于扩展新 Provider、Agent 和 Harness。
- **把 AI 护航做成独立业务模块**：护航必须理解所有状态并在所有步骤提供帮助，独立页面不能满足这个目标。

## 后续约束

- 新需求进入设计前，必须先标注唯一所有者。
- 发现跨模块复制事实时，先调整架构文档，再修改代码。
- 若未来确需改变模块所有权，新增 ADR，不直接改掉本决定的历史。
