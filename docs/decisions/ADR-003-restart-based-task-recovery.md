# ADR-003：恢复采用新批次重启，不自动回退项目文件

## 背景

S05 需要让失败或服务中断的 Pi 任务可以继续处理。现有系统已经有黑匣子事件、Git 前后快照、任务证据和 Pi 启动链路，但没有可靠的 Pi 会话续接能力。恢复如果直接执行 Git 回退，还可能覆盖用户在任务后产生的改动。

## 决定

1. 第一版只允许 `failed` 和 `interrupted` 任务恢复；用户主动 `stopped`、成功执行和已验收 `accepted` 的任务不提供恢复入口。
2. 恢复从黑匣子中读取已脱敏的原任务信息，在活动项目边界内创建一个新的 Pi 执行批次；不续接旧进程或旧会话。
3. 恢复前必须生成一次性预览，并在启动时重新校验项目 ID、分支、HEAD、工作区摘要和来源任务终态；任何变化都使预览失效。
4. 恢复不执行 Git 写命令，不修改、删除、覆盖或回退项目文件。文件回退必须另建切片、另做高风险确认。
5. 来源任务的历史记录只追加受控恢复事件，不覆盖原有内容；新任务保存 `sourceTaskId` 关联，继续使用现有任务证据、验收和 AI 交接闭环。
6. 总览只显示恢复摘要并跳转到项目执行面板；预览与确认由恢复服务和项目执行面板负责，避免总览建立第二套操作状态。

## 结果

### 正面结果

- 失败/中断任务可以在修复认证、服务或环境问题后快速重试，不必重新描述任务。
- 用户的项目改动不会因为点击恢复被自动覆盖或回退。
- 新旧批次独立可追溯，原始失败证据仍然保留。
- 预览指纹、单次句柄和单 Pi 锁降低误重放和重复启动风险。

### 代价与残余风险

- 新批次不是旧 Pi 会话的连续上下文；需要依赖脱敏任务记录和当前 AI 交接摘要。
- 恢复在当前工作区上重新执行，原任务产生的部分文件改动不会自动清理；用户必须在预览中看到改动摘要并自行决定是否继续。
- 服务重启会使未确认的预览失效，需要重新生成。
- 任务文本如果在来源记录中缺失或被安全脱敏，恢复会被拒绝而不是猜测。

## 未选择的方案

### Pi 会话续接

不采用。它依赖 Pi CLI 的会话存储、版本和认证状态，无法为当前 v0.1 提供稳定的跨重启契约。

### 自动 Git 回退

不采用。工作区可能包含用户既有改动和任务后的新改动；自动 `reset` 或 `restore` 会产生不可逆的数据损失风险。

### 总览页直接启动恢复

不采用。总览的唯一职责是只读聚合；确认、执行锁和错误处理必须由恢复服务与项目执行面板拥有。

## 后续约束

- 任何文件回退、检查点选择或跨项目恢复都必须新建设计和 ADR。
- 恢复路由不得接受浏览器传入的路径、命令或原始任务文本覆盖。
- 恢复完成前不得把 `failed` 或 `interrupted` 事实改写成 `accepted`；新任务必须走正常验证与用户验收。
